# 用修改稿训练 skill

这里的"训练"不是微调模型，而是 **规则库 + 样例库** 的持续进化：每一次人工修改都被提炼成可复用的规则。

## 触发

用户提供修改后的纪要，或说"这是我改好的""以后要这样""这条不重要""漏了 X"。

## 步骤

### 1. 对比差异并分类

把 AI 稿和终稿逐条对比，每处差异归入一类：

| 类别 | 含义 | 例子 |
|---|---|---|
| 漏项 | 终稿有、AI 稿没有 | 漏了"回去查 SOP"这个行动项 |
| 冗余 | AI 稿有、终稿删除 | 保留了某人对历史情况的长篇回顾 |
| 事实错误 | 人名、项目、数字、负责人写错 | 把 QC 的事归给了 QA |
| 术语错误 | 误识别没有纠正 | "天津寺"应为某基地名 |
| 定级错误 | 待决写成了已决，或反过来 | |
| 表述/结构 | 措辞、顺序、颗粒度 | 结论太长，应拆成两条 |

### 2. 提炼规则（核心步骤）

每类差异都要问一句：**这次修改背后的通用原则是什么？** 写成可执行、可检验的规则：

- 好规则："凡涉及放行或检测策略变更的讨论，必须单列议题，并写明需要谁拍板"
- 坏规则："要写槽车的事"（太具体，无法复用）
- 坏规则："要更准确"（无法检验）

一次修改最多提炼 3 条规则。纯个案的修改（例如某个错别字）不提炼规则，只更新术语表。

### 3. 规则生命周期

- 新规则：状态为 **试用**。
- 试用规则在后续 3 次纪要中被应用、且没有被用户推翻：转为 **生效**。
- 被用户推翻 2 次：转为 **废弃**。
- 新规则与已有规则冲突时：先向用户确认，不要两条并存。
- 规则总数超过 40 条时：建议用户合并相近规则。

### 4. 存样例

- 把"AI 稿 + 终稿 + 修改要点"存入样例库。
- 每个会议类型只保留最多 3 条示范，优先选修改量最大、最典型的。

### 5. 回写与汇报

向用户输出：

```markdown
### 本次学习
- 差异：漏项 X 处 / 冗余 X 处 / 错误 X 处 / 定级 X 处 / 表述 X 处
- 新规则（试用）：1. …… 2. ……
- 规则升级为生效：……
- 术语表新增：……
- 样例库：已存为「{会议类型}」示范 / 未存（原因）
```

工具模式下写入"学习规则"和"样例库"两张表；手动模式下，请用户把新规则追加到 `learned-rules.md`。

## 质量指标（用来证明"显著提升"）

每份纪要记录一行，存在样例库或单独的指标表中：

| 指标 | 计算方式 | 目标（需按基线校准） |
|---|---|---|
| 漏项数 | 终稿新增的结论和行动项条数 | 第 10 份起 ≤ 1 |
| 冗余率 | 被删条数 ÷ AI 稿总条数 | ≤ 10% |
| 事实错误数 | 人名、项目、数字、负责人错误 | 0 |
| 人工修改用时 | 用户自报（分钟） | 比基线降低 70% 以上 |
| 用户评分 | 1–5 分 | ≥ 4 |

建议先用现有千问模板出 3 份纪要，记录基线指标；再用本 skill 出同样 3 场会的纪要，做对照。这样能拿出前后对比的数据。
