# 一页式会议纪要（meeting-minutes-pro）

## 目标

产出**一页以内**（正文约 600–1000 字）的纪要，读者 1 分钟内能知道：定了什么、谁在什么时候交付什么、还有什么没定要谁拍板。

三条铁律：
1. **只保留四类信息**：议题、建设性观点、结论、行动项。寒暄、口头禅、重复、无结论的发散一律删除。
2. **禁止原文引用**。所有内容用书面语重写，每条一句话，主语明确。
3. **不编造**。负责人、截止时间、数字在原文中找不到的，写"未明确"，并放入"待确认"区；不要猜。

## 运行模式

- **工具模式（默认）**：调用 `dws`（`minutes` / `aitable` / `contact` / `aisearch` / `chat` / `doc` / `todo`），自动读逐字稿、读上下文库、解析人名、回写记忆。
- **手动模式（兜底）**：`dws` 调用失败时，用户粘贴逐字稿；上下文从 `references/` 下的文件读取；回写内容以"记忆更新块"输出，由用户复制到 AI 表格。

两种模式的处理步骤完全相同，只是输入和输出的通道不同。

## 处理流程

### Step 0 获取输入与元信息

- 有听记 `taskUuid` 或链接：`dws minutes +transcript --id <taskUuid>`，必须追完分页（`data.complete=true` 才算完整）。同时读取 `dws minutes +detail --id <taskUuid> --artifacts basic` 获取主题和时间。
- 有文件或粘贴文本：直接读取。
- 元信息缺什么就补什么：主题、日期、参会人、主持人。**最多问一次**，把所有缺项合并成一个问题。用户不答时按推断继续，并在纪要页眉标"参会人待确认"。

### Step 1 加载企业上下文

按 `references/context-schema.md` 从上下文库读取：
1. **术语纠错表**：全部读取（用于 Step 2）。
2. **项目卡片**：用逐字稿中出现的项目名、别名、物料、设备、基地等关键词匹配，取命中的卡片。
3. **人员表**：取参会人，以及逐字稿中出现的姓名或称呼命中的记录（职位、负责事项、与我的关系、决策权限）。
4. **历史决议与未关闭行动项**：取命中项目最近 3 次会议的决议，以及状态非"完成"的行动项。
5. **学习规则**：读取状态为"生效"和"试用"的规则（库中没有时读 `references/learned-rules.md`）。
6. **样例**：按会议类型取 1–2 个修订样例（库中没有时读 `examples/`）。

上下文只用来**纠错、补背景、判断重点**，不得把上下文中有、但会上没讲的内容写进纪要。

### Step 2 清洗与纠错

1. **术语纠错**：按术语纠错表替换（例如同音误识别的基地名、项目代号、方法编号）。表中没有、但明显是专有名词误识别的，**不擅自改**，在内部清单中记为"疑似误识别：原词 → 推测"，最后放进纪要末尾的"待确认"区和记忆更新块。
2. **人名解析与说话人映射**：按 `references/person-resolution.md` 执行，有时间盒限制，解析不出来就标"待确认"，不拖慢纪要。
   - 解析顺序：人员表 → 通讯录（`dws contact +lookup` / `dws aisearch person`）→ 必要时看近 30 天聊天记录（`dws chat +search-msg`），区分同名候选并初判负责事项。
   - 说话人映射：结合称呼、自述职责、人员表中的"负责事项"推断身份。把握大时直接用姓名；把握不大时写"说话人2（疑似张三）"，并列入待确认。
   - 行动项的负责人必须是具体的人；推断不出来时写"未明确"。
   - 新的人或新的称呼，写入记忆更新块的"人员新增/更新"。
3. **降噪**：删掉口头禅（"对吧""那个""嗯"）、自我重复、打断后的半句话、与会议主题无关的闲聊。

### Step 3 议题切分与信息分级

先按话题转换切成议题。一般会议有 2–6 个议题；超过 6 个时，合并同一项目下的小议题。

每个片段打一个等级，详细判定标准见 `references/extraction-rules.md`：

| 等级 | 含义 | 处理 |
|---|---|---|
| A 决议 | 明确拍板、否决、选定方案 | 必须保留 |
| B 行动 | 有人承诺或被指派去做某事 | 必须保留，结构化 |
| C 建设性观点 | 提出方案、给出依据或数据、指出风险或约束、提出替代思路 | 每个议题保留不超过 3 条 |
| D 背景 | 现状描述、历史回顾 | 压缩为一句，放在议题开头 |
| X 噪音 | 寒暄、跑题、重复、情绪、无依据的抱怨、无结论的发散 | 删除 |

### Step 4 结构化抽取

每个议题抽取以下字段：
- `关联项目/对象`：必填，优先使用项目卡片中的标准名。确实无关具体项目的，写"通用/管理"。
- `议题`：一句话问题陈述，写成"要解决什么"，不要写"讨论了什么"。
- `关键观点`：不超过 3 条，格式为"谁 + 主张 + 依据/理由"。
- `结论状态`：已决 / 待决（需谁拍板、何时） / 否决。
- `行动项`：事项（动词开头）、负责人、截止时间、交付物/完成标准。

### Step 5 按模板生成纪要

严格使用 `references/one-page-template.md`。排序原则：**结论 → 行动项 → 议题要点 → 待决与待确认**。

### Step 6 自检（不通过则修正后再输出）

- [ ] 每个议题都标了关联项目
- [ ] 每条结论都能在逐字稿中找到对应依据（内部核对时间戳，正文不展示）
- [ ] 每条行动项都有负责人；缺截止时间的已标"未明确"
- [ ] 没有原文引用，没有口语词
- [ ] 正文不超过 1000 字；超出时先删 C 级观点，再压缩背景
- [ ] 已应用全部"生效"规则
- [ ] 上下文中有、但会上没讲的内容没有混入正文

### Step 7 输出与记忆回写

1. 输出纪要正文。
2. 输出**记忆更新块**（格式见 `references/context-schema.md`），包括：新决议、新行动项、项目卡片的"最近进展"、人员新增/更新、术语候选、本次会议索引。
3. 请用户回复"确认回写"后再写入 AI 表格：
   - 先写人员和会议索引，拿到 recordId；
   - 再写决议和行动项，关联字段的值为 `{"linkedRecordIds":[...]}`；
   - 新记录用 `dws aitable record create`，已有记录用 `dws aitable +record-update`；
   - 写入后回读验证。
4. 用户要求时：用 `dws doc` 生成钉钉文档，或用 `dws todo` 把行动项建成待办。

### Step 8 学习（用户给出修改稿时触发）

用户说"这是我改好的""按这个改""以后要这样"，或直接贴出修订版时，按 `references/feedback-loop.md` 执行：
1. 对比差异；
2. 提炼通用规则；
3. 存入样例库；
4. 更新规则状态；
5. 记录质量指标。

## 冷启动（首次使用）

上下文库为空时，按 `references/context-schema.md` 中的"冷启动"一节，先用 5–10 份历史逐字稿批量提取术语、项目和人员的候选，由用户确认后入库。冷启动期间也可以正常出纪要，只是待确认项会多一些。

- `references/learned-rules.md`：规则库（离线备份，初始种子规则）
- `examples/`：修订样例（AI 稿 → 人工终稿）
