PART 01 · 为什么是现在

每年 200+ 份技术报告 · 资深工程师 30% 工时被"机械汇编"占用

业务痛点

🔴 工程师产能浪费
  • 5 工作日 / 份 × 200 份 = 1000 工作日 / 年 ≈ 4 个全职工程师
  • 其中 700 工作日（70%）是"机械活"
  • 资深工程师本应做"工艺优化"，被报告拖住
🔴 报告质量不一致
  • 不同工程师写出来的同类报告结构不一致
  • 数据漏项、图表标错、引用不一致 — 客户审计时常被指出
  • 新人写报告需要 2-3 倍时间
🔴 监管 / 客户要求越来越高
  • FDA / NMPA 要求 APR 数据可追溯 + 趋势分析
  • 客户技术报告要求 7-14 天内交付（越来越紧）
  • QbD / PAT 体系下报告需要包含的数据维度比 5 年前多 2-3 倍
💡 为什么是"AI 不烧钱也能见效"的最佳实证
  • 不涉及生产决策 — 不动 GMP 严管的"放行 / 投料"流程，监管敏感度低
  • 有兜底 — 工程师审核签字流程不变，AI 出错最多被改掉，不会发到客户
  • 价值显性 — 每份报告省 4 工时，规模化后 800 工时/年起步
  • 技术成熟 — 市场上 LLM + RAG 方案非常成熟，DeepSeek / 通义 / 盘古都可选
  • 团队接受度高 — 让工程师"少干苦活"，业务部门主动配合

PART 02 · 凯莱英现状盘点

底座 80% 就绪 · 缺的是把数据"汇编 + 套模板"的最后一公里

凯莱英其实已经做了大量"数据沉淀"的工作 —— MES / LIMS / QMS / SAP / EAM 都在跑。 缺的不是数据，是"跨系统取数 + 按模板填充 + 自动生成图表"这一层。

核心判断：
  • 凯莱英不是"从零起步"，80% 的底座已经在，缺的是"把数据汇编 + 套模板"那一层 AI
  • 最大工程量在跨系统取数中间层（IT 主责，4-8 周）+ 模板结构化（业务主责，2-4 周）
  • LLM 选型可外采（DeepSeek 私有化 / 通义企业版 / 华为云盘古），不需要从头训练

PART 04 · 技术路线 — 可复用、可解释、可审计

跨系统取数 → 段落级 RAG → 模板填充 → 工程师定稿

架构上不复杂，关键在"段落级 RAG"这个设计选择 —— 不让 LLM"自由发挥",而是把每个段落的内容来源严格绑定到原始数据 / 历史段落， 从根上规避 LLM 的"幻觉"问题，满足合规审计要求。

关键设计 · "段落级 RAG"

传统 LLM 用法是"输入数据 + 模板 → 输出报告"，但这种方式有幻觉风险（LLM 会自己编数字）。 我们采用"段落级 RAG"设计：

  • 每个报告章节 → 拆成若干段落，每个段落有自己的"数据来源类型"（KPI 表 / 趋势图 / 偏差总结 / 结论建议 等）
  • 每种数据来源类型 → 走不同的生成路径：
    • "批次清单 / KPI 表"：从 MES / LIMS 直接硬填充，不让 LLM 改数字
    • "趋势图 / Pareto"：从数据计算结果渲染成 SVG / 图片，不让 LLM 画图
    • "偏差描述 / CAPA 总结"：用 LLM 改写，但每段都附原始 QMS 记录链接
    • "结论 / 改善建议"：LLM 提供 3-5 个候选，工程师选 / 改 / 自己写
  • 每个段落都附"引用源"标签，可点击跳转原始数据 → 合规审计可追溯
为什么这个设计能满足合规：每个数字、每段引用都可追溯到原始系统记录；LLM 只在 "改写已有内容"和"提供候选建议"两个有限场景介入；工程师审核时每段都能看到来源。 GAMP 5 验证时可以明确"哪些是 AI 决策、哪些是数据搬运"。

  • 跟方向 ⑥ 培训生成共用同一套 LLM + RAG 底座，边际成本接近 0
⚠️ 路线 B / C 何时考虑
  • 路线 B（盘古制药）：如果凯莱英已有华为云战略合作 → 谈优惠价值得；制药案例库是真亮点
  • 路线 C（埃森哲）：如果集团要做全方向 AI 战略总集成（不只是报告），且预算充足，埃森哲适合做"伞型"合作；但单独做报告 AI 性价比低
  • 无论 B/C，都不能让供应商持有凯莱英 RAG 索引（客户数据资产保留在凯莱英）

PART 10 · 决策建议

重点决策 4 件事

①
立项 — 作为 Quick Win #1 启动

建议立即立项本方向 PoC（50-80 万预算 / 3 个月周期）。 本方向是 6 个 AI 方向里"最快出成果、最低风险、最高接受度"的，适合作为给副总裁 / 集团 / 客户展示 "AI 不是 PPT"的实证。配合方向 ⑥ 培训生成一起做，可共用 LLM + RAG 底座。

  • 决策项：PoC 立项 + 预算 50-80 万 + 团队 5-8 人
  • 启动条件：跟 IT 对接人开 1 次 kick-off 会议即可
②
技术路线 — 推荐 A+D 混合

建议先用路线 A（通用 LLM API + 自建 RAG）跑 PoC，3 个月内见效； Pilot 阶段转路线 D（DeepSeek 满血版私有化 + RAG）避免数据出境和调用费不可控。 埃森哲 / 华为云盘古制药不作为本方向第一选项（性价比不如自建）。

  • 决策项：LLM 路线 A→D；不绑定外采全包方案
  • 关键约束：RAG 索引 100% 凯莱英所有，供应商无权持有
③
范围控制 — PoC 严格 1 种报告 × 1 个项目

本方向最大陷阱是"啥都想做" —— 同时上 Campaign + MOR + APR、覆盖所有客户、做多语言。 PoC 阶段必须严格限定1 种报告（Campaign Report） × 1 个项目（主力商业化 API）， 跑通后再扩大。

  • 决策项：PoC 范围由"工艺研发主任 + IT 对接人 + QA 主管"3 方书面确认
  • 变更控制：PoC 阶段不允许加范围（Pilot 才放开）
④
PoC 验收标准 — 提前对齐

PoC 阶段（M3 末）必须有明确的 Go / No-Go 标准。建议： ① 10 份历史 Campaign Report 回测；② AI 草稿采纳率 ≥50%； ③ 每段都有引用源链路；④ 工程师验收时间 ≤1 天/份。 4 条都达标才进 Pilot；不达标则评估是模型问题还是数据问题，决定继续优化或停止。

  • 决策项：验收标准跟 QA / 工艺研发 / IT 三方确认 + 写进 PoC 合同
  • 不达标的兜底：30 万沉没成本上限 + 资产保留（数据中间层 + RAG 索引归凯莱英）
