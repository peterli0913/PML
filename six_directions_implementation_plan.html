PART 00 · 总体推进 · 一张大图说清楚

6 方向不是 6 个独立项目 — 共享 4 大基础设施 + 互相依赖

所有方向都依赖共同的基础设施 + 数据底座。基础设施先做、共享，则 6 方向可以并行 / 渐进推进； 基础设施不做，每个方向都要自己重建一遍，会严重浪费投入。 这是本方案最重要的洞察 —— 不要把 6 方向当 6 个独立项目立项。

0.1 · 依赖关系网图 — 6 方向 + 4 共同基础设施

💡 核心洞察 · 跟 IT 沟通时的第一句话

不要把 6 方向当成 6 个独立项目立项。它们共享 4 大基础设施（数据底座 / 主数据治理 / 客户隔离 / AI 平台底座）。 正确做法：

  • 基础设施作为独立的 1 号项目立项—— 由 IT 主责 + 业务全力配合
  • 6 方向以"应用项目"形式跟随基础设施推进—— 基础设施做到什么程度，能跑什么方向
  • 方向 ②（报告）+ ⑥（培训）依赖最浅 → 可以最早做出来当 Quick Win
  • 方向 ①（QC）+ ③（技转）依赖最深 + 监管最严 → 长期战略性投入

1.2 · MVP 范围（先做小，再放大）

✅ MVP 第一版做的
  • 1 个商业化项目（如某主力 API）
  • 预测 3 个核心 CQA：含量 / 杂质 A / 水分
  • 预测窗口：批结束前 2 步 ~ 完批时给出预测
  • 输出：在 LIMS 中嵌入"AI 预测"区块（不替换 QC 检测）
  • QC 工程师审核签字流程完全保留
❌ MVP 不做的（避免范围蔓延）
  • 不做"用 AI 替代 QC 检测"
  • 不做跨客户数据混训
  • 不做晶型 / 粒度等复杂 CQA（这些放到 V2）
  • 不做"AI 自动放行"（始终人工签字）
  • 不做实时干预（第一版只做被动预测，不做主动报警停机）

1.3 · 数据流 + 系统集成架构

1.4 · IT 侧 vs 业务侧职责清单

🟦 IT 侧职责（数据 + 平台 + 集成）
  • 数据接口：IP.21 / LIMS / EBR / SAP / EAM 历史数据 ETL + 实时 API
  • 数据中间层：跨系统统一批次 ID + 元数据治理
  • AI 平台部署：供应商方案上线 + 模型托管 + GPU 资源调度
  • LIMS UI 集成：在 QC 工作台嵌入"AI 预测"卡片
  • 权限管理：项目级数据访问 + 客户隔离
  • 合规支持：审计日志 + 数据血缘 + GAMP 5 验证文档
  • 运维监控：模型准确率监控 + 模型漂移告警
🟩 业务侧职责（数据语义 + 验证 + 流程）
  • CPP / CQA 字典：QC + 工艺研发 提供每个项目的关键参数定义
  • 历史批次标注：标注合格 / 不合格 / 偏差批 + 根因
  • 放行决策规则：QA 提供 SOP + 监管要求
  • 预测验收标准：业务认可的"准确率 80%" 含义
  • UAT 测试：QC 工程师试用 + 反馈
  • 变更管理：QC SOP / 培训材料更新
  • 监管应对：客户审计 / FDA 检查应对材料准备

7.1 · 联合工作节奏

📅 周节奏

  • 周一站会 30 分钟：上周复盘 + 本周计划
  • 周五同步 15 分钟：风险升级 / 决策需要
  • 双方各派 1 个 PM 角色（IT + 业务）

📅 月节奏

  • 月度 Review 1.5 小时：方向负责人 + IT + 业务部门负责人
  • 每方向 1 张状态卡片（绿黄红）
  • 风险升级 + 资源调整 + 决策点

📅 季度节奏

  • 季度 Steering Committee：副总裁 + 各部门负责人
  • Quick Win 成果展示 + 预算 / 资源调整
  • 下季度优先级调整
